### Native acceptance sequence

1. Register two disposable email accounts against the local endpoint. Sign out and back in, relaunch to check session persistence, and use an incorrect password to check the error state.
2. Open public and private profiles from a post and from the follower list. With the two accounts, request, accept, unfollow, refresh the list, and compare both counts. Return with the back button and iOS swipe gesture.
3. Create posts with one and ten synthetic photos, try to add an eleventh, and check preview and ordering. With the other account, like and comment, then open notifications and check the destination.
4. Verify that a non-follower cannot see the private photo or posts. Check access after acceptance, unfollow, and block. Repeat for any signed link already issued.
5. Repeat the key routes in Arabic and English. Check mirrored back controls, clipping, large text, retry states, and denied or expired photo loads.
6. Delete one disposable account through Settings against the local handler, then verify its account and files are gone and the second account still works. Never use a live account for this step.

Keep the bucket private. Five minutes is a reasonable interim app default if the product accepts an existing-link grace period. The app currently requests one hour, caches URL strings in memory by bucket and path, refreshes a link when less than one minute remains, and clears that cache on sign-out. Five-minute signing would leave about four minutes of normal URL reuse. The avatar renderer also uses Expo Image's default disk cache, which is separate from the URL map. For private avatars, avoid disk caching and discard URL and view state when authorization changes. Verify image refresh on long-lived screens before shipping a shorter lifetime.

A five-minute client default cannot enforce an upper bound while the same viewer can call Storage signing directly. Supabase's hosted Smart CDN can retain cached responses beyond token expiry. If blocking must stop future online delivery immediately, require an authenticated photo-serving endpoint that checks current block and visibility on every request, serves bytes with `Cache-Control: private, no-store`, and closes direct viewer signing and download paths. Preserve owner-only writes and validate the path against the owner's active photo. Test warm-cache, expired-token and blocked-viewer cases through the hosted test gateway. Already downloaded images and retained legacy public URLs are separate exposure paths. Legacy public originals remain subject to the existing cleanup approval gate. [Supabase downloads](https://supabase.com/docs/guides/storage/serving/downloads) · [Smart CDN](https://supabase.com/docs/guides/storage/cdn/smart-cdn)

## Native release blocker fixes

The comment query was returning rows under the synthetic user's RLS permissions. General sync built its replacement state with `emptyEntities()`, which emptied the per-post comment cache after notification read or comment submission triggered a sync. The fix preserves independently loaded comments for the same signed-in account, removes comments from locally blocked authors, and discards in-flight comment loads on an account change. The iOS navigation stack was using its default direction while Haratna mirrored only the app's controls. The root stack now receives the active locale through Expo Router's `LocaleProvider`. ## Lost responses and partial photo batches

The loopback proxy observed HTTP 201 before dropping the response to the client. Retrying the current post and comment requests produced two rows each. The stable UUID prototype used the existing primary key and reconciled to one row each. It also rejected a mismatched payload and author. The app integration remains a release gate.

With an interrupted two-photo batch, the first photo survived and the second upload and cleanup requests were disconnected. Retrying verified and reused the first file, uploaded the missing file, and completed one post. Fixture-scoped cleanup removed abandoned files and preserved the completed post and other user's bytes. The present trigger still accepts a reference after object removal, so automated cleanup requires a publication fence. The current owner cleanup path also removed a committed post's file after the response was dropped.

The four original patches apply cleanly in order. The build plan, cleanup security model, remaining gates, and residual risks are recorded in the [resilience handoff](HARATNA-SOCIAL-RESILIENCE-HANDOFF.md). [Probe results](social-validation/final-resilience.log)
